OpenDrop implements sending from Linux to Apple receivers when an AWDL transport
is available. This capability predates the latest revisions; it is not a new
upstream fix for our BCM4378 or current macOS/iOS. OWL supplies the link layer;
Omdrop currently advertises receiving, and LocalSend uses a separate protocol.

## Reference sequence and Rust implementation

1. Discover the receiver's scoped IPv6 address and service port. The discovery
   client has its own connection and posts a binary plist to `/Discover`.
2. Create the transfer connection. OpenDrop uses OpenSSL via Python's HTTPSConnection.
   The new Rust client uses tokio-openssl and Hyper's HTTP/1.1 connection API.
3. Send binary-plist `/Ask` metadata, including SenderID and file name/type/path.
   Wait for HTTP 200 before uploading. Declines stop the transfer.
4. Reuse the same owned transfer connection for `/Upload`. Reconnect only if
   the Ask response closed it; never automatically replay an ambiguous Upload.
5. For files, declare `TransferID = { id = UUID }` and `TransferType.files` in
   `/Ask`. Send DVZip-wrapped odc CPIO as `application/x-dvzip`, using HTTP
   chunked framing. Repeat that exact UUID on `/Upload`, together with
   `TotalBytes`, `SenderPseudonym`, `SenderPushToken`, and `Expect: 100-continue`.
   Links remain Ask-only transfers.
6. Consume the HTTP response with explicit framing and size limits. Only a
   complete HTTP 200 response makes the UI report delivery.

The Rust implementation retains disk-backed archives, folder support, approval,
cancellation, progress and response limits. It does not copy GPL Python code.
The HTTP protocol implementation is Rust; TLS uses OpenSSL through Rust bindings.

## Differences removed

- Replaced reqwest's connection pool with one owned transfer connection.
- Removed the unsuccessful force-a-new-connection-for-every-endpoint experiment.
- Matched OpenDrop's TLS library and direct IP endpoint; no artificial
  `airdrop.local` DNS/SNI name. IPv6 scope remains on the socket address.
- Uses conventional header casing, keep-alive and the Airdrop-compatible user agent.
- Correlates the accepted request and upload with one UUID. A proven Linux/iOS
  implementation identified the missing correlation as the reason Apple
  rejected Upload before reading its body.
- Uses Apple's current DVZip container and upload identity/header shape.
- Removed the library's implicit 15-second keepalive/30-second TCP_USER_TIMEOUT.
  Connect, TLS and request operations retain explicit finite deadlines.
- Uses the canonical zero-mode/inode odc trailer generated by libarchive.

Intentional differences: no legacy TLS below 1.2; no claimed Apple ID/Contacts
Only verification; response compression is not advertised; payloads stay on
disk rather than in RAM. Application code and archive handling remain Rust.

## Validation

86 regular tests pass, with the external decoder test ignored in the default
suite and separately run successfully against installed bsdtar/libarchive.
Clippy with warnings denied passes. Coverage includes certificate presentation,
separate discovery, same-socket Ask/Upload, explicit-close reconnection, shared
Ask/Upload transfer ID, chunked DVZip/CPIO, acceptance and decline, empty success followed by TLS shutdown,
100 Continue followed by chunked response, close-delimited responses and rejecting
truncated responses. Existing large-file, folder and cancellation tests pass.

These checks validate local behavior, not Apple-device success. The prior Mac
upload failure remains unconfirmed as fixed until the user tests this build.
Session IDs and local/remote socket addresses now allow matching Linux requests
to Mac sharingd events without logging file content or private keys.

## Stale UI correction

The first reported failure after installation still named airDrop.local/reqwest.
Inspection found the visible window belonged to PID 1825547, started before the
upgrade and running deleted /usr/bin/ac-dc version 0.2.1. The new process had
forwarded GTK activation to that old instance, then remained headless waiting
for its worker. Therefore that report did not test the new sender.

Package 0.2.2-2 adds the version to the window title, presents an existing window
on subsequent activation, and shuts down the secondary invocation's worker when
GTK returns. The stale window and headless process were stopped while idle.
